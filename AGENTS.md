# Инструкции для следующего агента

## Начать здесь
1. Прочитайте `docs/HANDOFF.md` — архитектура, история, результаты проверок, риски и следующие шаги.
2. Прочитайте `README.md` — пользовательский запуск, backup/restore и выпуск версий.
3. Проверьте `git status --short`, текущую ветку и актуальные исходники: документация описывает срез, а не заменяет код.
4. Перед изменением контракта API изучите одновременно `cmd/server/main.go`, `cmd/client/main.go` и `internal/web/index.html`.

## Контекст проекта
- Пользователь общается на русском. Запрос: Windows setup.exe, Go + HTML GUI, клиент/сервер, БД, логин/пароль, backup по расписанию, GitHub Actions после изменений, обновления через GitHub.
- Реализован стартовый проект Pulse, не готовая предметная бизнес-система.
- GUI сейчас в браузере, не WebView. Сервер отдельно, не Windows service.
- Модуль: `github.com/pmstein71-ui/testtest`. Go 1.23+, SQLite через modernc (без CGO).
- Ветка этой передачи: `arena/e0a8610f-testtest`. В агентской среде следуйте актуальному указанию о текущей ветке; не переключайтесь самостоятельно, не делайте merge/release без запроса.

## Правила работы
- Не добавляйте в Git базы, пароли, ключи, бэкапы и EXE. `dist/` и `data/` игнорируются.
- Не ослабляйте HTTPS удалённого сервера, Host/Origin-проверки и обязательный `X-Pulse-Client` у локального клиента.
- Не считайте SHA-256 цифровой подписью установщика.
- После правок Go: `go mod tidy`, `gofmt -w cmd internal`, `go vet ./...`, `go test -race ./...`.
- В репозитории пока нет `go.sum`: создайте и сохраните его при первой доступности Go, см. HANDOFF.
- После согласованных изменений отправляйте текущую ветку и проверяйте Actions: пользователь просил сборку сразу после изменений. Не ограничивайтесь фактом отправки push.
- Не выдавайте успешную компиляцию за проверку установки, авторизации, backup/restore и обновления на настоящей Windows.
- Поддерживайте `README.md` и `docs/HANDOFF.md` актуальными. Секреты и данные аутентификации в документацию не записывать.
